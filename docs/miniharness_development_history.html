项目快照：当前到底有哪些东西？

先从仓库地图认识工程，而不是一上来逐行读代码。

项目定位

MiniHarness

一个以命令行作为入口、使用真实模型 API、可执行受控工具、能够在临时副本中修改项目，并允许人工审查和回写的轻量级 Coding Agent Harness。

技术选型

TypeScript + Node.js

TypeScript 提供类型约束；Node.js 提供文件、网络、子进程和 CLI 能力；pnpm 管理依赖；Vitest 承担自动化测试；tsx 直接运行 TypeScript。

为什么这些模块要分开？

模块核心职责不应该承担的职责
agent.ts控制模型与工具循环、维护本次消息历史、决定何时停止。不直接写 HTTP 细节，也不内嵌所有文件系统实现。
http-provider.ts把内部消息转换为 API 协议，发送请求并解析响应。不执行工具，也不决定工具权限。
registry.ts保存工具定义与 handler，并根据名称分发调用。不决定某次调用是否需要用户批准。
policy.ts + CLI 授权函数给出 allow/ask/deny 决策，并在 ask 时询问用户。不是操作系统级权限隔离。
runtime/统一执行进程、管理工作区、比较文件并回写。当前不是 Docker / VM 后端。
observability/保存和分析运行事件。不会自动把旧任务记录变成新任务的记忆。
02

开发历程：系统是怎样一步步长出来的？

由聊天记录与当前代码结构反向重建，不冒充精确的 Git 历史。

STAGE 0 · PROJECT BOOTSTRAP

建立 TypeScript 项目骨架

先让工程能运行、能做类型检查、能执行测试。项目使用 ESM（"type": "module"）、NodeNext 模块解析和 pnpm scripts。

留下的工程资产：package.json、tsconfig.json、Vitest 测试入口与启动检查。

STAGE 1 · MODEL BOUNDARY

把模型 API 封装成 Provider

用户明确采用 DeepSeek 官方 API。系统没有把 API 调用散落在 Agent 逻辑中，而是通过 ModelProvider 接口与 OpenAICompatibleProvider 隔离模型协议。

关键收获：API Key / Base URL / Model 是配置；SDK 不是必需品。也可以直接用 fetch 发送 HTTP 请求，由自己维护协议转换与错误处理。

STAGE 2 · AGENT LOOP

实现“模型决策—工具执行—反馈—再决策”

Agent 初始化 system/user 消息，循环调用 Provider；收到 tool call 后分发执行，把 tool result 追加到历史，再次请求模型；没有 tool call 时返回最终答案；超过 maxSteps 时停止。

关键收获：Agent 不只是一次 LLM 请求，Agent Loop 才是持续执行任务的控制结构。

STAGE 3 · TOOLS & GUARDRAILS

建立工具注册、参数解析和权限策略

工具通过 JSON Schema 暴露给模型；Registry 解析模型返回的 arguments；Policy 对只读工具自动放行，对编辑和测试操作要求审批，未知工具拒绝执行。

关键收获：模型提出调用，不代表工具一定执行。调用意图与执行权限是两个步骤。

STAGE 4 · RUNTIME

把子进程执行从业务工具中抽离

增加固定检查工具、超时控制、输出截断和进程树终止。Windows 下需要处理 cmd.exe / pnpm 启动差异，POSIX 与 Windows 的进程树终止方式也不同。

关键收获：“运行命令”不是一行 spawn 就结束，还要考虑超时、输出规模、退出码和子进程。

STAGE 5 · OBSERVABILITY

让 Agent 的行为可追踪、可复盘

定义生命周期事件并写入 JSONL。Trace Reader 校验记录并统计模型请求、工具调用、失败数、持续时间等。

关键收获：系统不能只输出一句最终回答；需要可追溯的执行证据。

STAGE 6 · WORKSPACE ISOLATION

把编辑对象从原始项目改为临时副本

工作区复制到系统临时目录下的 miniharness-sandboxes/run-*。复制时排除依赖、Git 元数据、环境文件和轨迹目录，并跳过符号链接。

关键收获：文件工具的 workspace root 是一个边界，但这还不等于操作系统级隔离。

STAGE 7 · DIFF & BASELINE

从“副本修改”走向“修改可审查”

先用 SHA-256 做文件级新增、修改、删除检测，再用 LCS 生成行级差异。创建工作区时保存基线快照，用来识别用户是否同时修改了原始文件。

关键收获：Diff 解释“改了什么”；Baseline 解释“原文件是否还是当初那一版”。

STAGE 8 · WRITEBACK

加入逐文件审批和选择性回写

写回前重新计算差异并检查状态；只接受显式批准的路径；新增使用独占创建，修改使用临时文件替换，删除前保存原始内容以便尽力回滚；最后验证批准文件是否仍有差异。

关键收获：“Agent 修改了副本”与“Agent 可以覆盖原项目”之间必须有明确的交付边界。

STAGE 9 · END-TO-END

通过 CLI 验证拒绝、批准和结果一致性

使用演示文件创建新任务，在 --diff 查看变更；--apply 先拒绝后批准；最后再次检查 Diff，确认批准文件已与原项目一致。

聊天记录中的验收结果：用户确认完整端到端流程全部通过。

STAGE 10 · CURRENT DECISION

先冻结 MVP，再讨论 Docker 与长期记忆

用户决定 Docker 暂时放一放，先理解当前架构。当前消息历史主要是单次 run 内存状态，Trace 是磁盘记录；跨任务长期记忆尚未实现。

当前目标：梳理代码与设计边界，而不是为了“功能更多”继续堆模块。

总体架构：这不是一个单文件 Agent

按运行时依赖关系阅读，比按文件名逐个看更容易建立心智模型。

系统最重要的分层思想

Decision

Agent Core

决定下一步要问模型什么、执行哪个工具、何时结束。

Mechanism

Tools / Runtime

把模型意图转换为受约束的实际操作，并拿到真实执行结果。

Governance

Policy / Delivery

限制可执行行为，并决定修改如何经过审查进入原项目。

04

Agent Loop：Harness 的控制中枢

核心文件：src/agent/agent.ts

Agent 的核心不是模型本身，而是围绕模型建立的控制循环。模型给出下一步决策；Harness 决定如何执行这个决策、怎样反馈结果，以及何时停止。

按源码解释一轮执行

  1. 初始化消息。run(task) 创建局部的 messages 数组，初始包含 system prompt 与 user task。
  2. 进入 step 循环。在请求模型之前更新 currentStep，并发出 model_request 事件。
  3. 向 Provider 请求。传入消息历史和 Registry 当前注册的工具定义。
  4. 记录 assistant 响应。把 assistant message 追加到历史，再读取 tool_calls。
  5. 判断结束条件。没有工具调用就返回 completed；存在工具调用则进入执行分支。
  6. 执行每个工具。先调用授权函数；拒绝时将拒绝信息作为工具结果，批准时由 Registry 执行。
  7. 把工具结果回填历史。每个调用结果以 role: "tool" 与 tool_call_id 追加到消息数组。
  8. 下一轮再问模型。模型可据工具结果决定继续调用工具，或生成最终回答。
  9. 处理异常与上限。模型请求失败会记录 model_error 并结束为 failed 事件；达到最大轮数返回 max_steps。

关键代码：工具结果如何回流

messages.push(assistant);

const toolCalls = assistant.tool_calls ?? [];

if (toolCalls.length === 0) {
  return {
    status: "completed",
    finalMessage: assistant.content ?? "",
    steps: step,
    messages,
  };
}

for (const call of toolCalls) {
  const approved = this.authorizeTool
    ? await this.authorizeTool({
        toolName: call.function.name,
        argumentsJson: call.function.arguments,
      })
    : true;

  const content = approved
    ? await this.registry.execute(
        call.function.name,
        call.function.arguments,
      )
    : `Tool execution denied: ${call.function.name}`;

  messages.push({
    role: "tool",
    tool_call_id: call.id,
    content,
  });
}
为什么要让模型再次看到工具结果？工具调用本身只是一个意图。只有把执行后的真实结果反馈给模型，模型才能依据事实继续决策，而不是假设工具一定成功。

当前 Agent Core 的边界

已实现还未形成完整能力
串行工具调用、工具结果反馈、maxSteps、事件回调、错误回填。持久化任务状态、暂停/恢复、复杂计划树、并行工具调度、动态预算管理。
每次 run() 有独立消息历史。跨 run 自动加载长期记忆或历史任务摘要。
系统提示词约束读写流程与检查结果。完整的结构化计划验证器、策略 DSL、自动化评估框架。
05

模型接入：为什么自己写 Provider，而不是必须装 SDK？

核心文件：src/model/types.ts、http-provider.ts、scripted-provider.ts

你在开发中问过：为什么要安装真实模型 SDK？不是给 API 和 Key，然后其他部分自己写吗？这正好引出一个关键的架构设计：模型服务是外部依赖，Provider 是系统的适配边界。

真实调用

OpenAICompatibleProvider

使用 Node 的 fetch 发 HTTP 请求，配置 API Key、Base URL 和模型名称，解析响应并转换成内部的 AssistantMessage。

测试调用

ScriptedModelProvider

按预设顺序返回模型消息，不需要联网或消耗 API 额度，适合测试 Loop、工具反馈和停止条件。

内部协议与外部 API 协议

export interface ModelProvider {
  complete(
    messages: ChatMessage[],
    tools?: ToolDefinition[],
  ): Promise<AssistantMessage>;
}

Agent Core 只依赖这个接口。HTTP Provider 负责把内部消息转换为 Chat Completions 风格的 payload，向 {baseURL}/chat/completions 发 POST 请求；它设置 Bearer Authorization、JSON Content-Type 和请求超时。

Provider 实际承担的责任

  • 校验 apiKey、baseURL、model 不能为空。
  • 清理 Base URL 末尾的斜杠，构造 endpoint。
  • 按消息 role 转换字段，assistant 消息可能携带 tool_calls 与 reasoning_content。
  • 使用 AbortSignal.timeout 处理请求超时。
  • 校验 HTTP 状态、JSON 格式、choices[0]、assistant message、content 和 tool call 结构。
  • 将 API 错误转换为可读异常，避免 Agent Core 依赖某个服务商的原始响应结构。
DeepSeek reasoning_content 的教训聊天中曾专门讨论思考模式返回的 reasoning_content。它不是用户最终答案，而是协议状态的一部分；Provider 需要在模型要求时保留并回传，不能随意丢弃，也不应把它当作普通用户可见日志输出。

为什么还要有 Scripted Provider？

如果每个单元测试都请求真实模型，测试会受到网络、速率限制、模型随机性和费用影响。Scripted Provider 让测试可以精确规定“第一轮模型发出工具调用、第二轮返回最终回答”，从而把 Agent Loop 的正确性与模型服务的可用性解耦。

06

Tools、Registry 与 Policy：从“模型提议”到“受控执行”

核心文件：src/tools/registry.ts、policy.ts、filesystem.ts、check.ts

当前注册的主要工具

工具名用途当前策略
list_directory列出工作区目录条目。allow
read_file读取工作区文本文件。allow
search_files在受限范围内搜索文件内容。allow
edit_file通过精确 old_text / new_text 修改文件。ask
run_check运行固定的 typecheck 或 test 检查。ask
echo返回输入字符串，用于诊断。Policy 函数未将 echo 列入 allow/ask，因此在当前 CLI 授权接线中会默认 deny；它主要是诊断工具。

Registry 为什么存在？

ToolRegistry 保存每个工具的 JSON Schema 定义和 handler。它拒绝空名称与重复名称；执行时按工具名称查找 handler，解析 arguments JSON，并要求顶层参数是对象。未知工具和非法 JSON 会被拒绝。

编辑工具为什么要求 old_text 唯一匹配？

模型先读取目标文件，再根据真实内容构造 old_text。工具会在原始文本中统计精确、非重叠匹配次数：必须恰好出现一次，否则不做任何修改。这个设计可以避免字符串重复时“猜测该改哪一处”。文件工具还有路径边界、符号链接解析、文件大小和搜索深度/结果数限制。

工程原则不要把模型输出直接拼成 shell 命令。当前 run_check 只接受 typecheck 和 test 两种枚举，再映射为固定命令，而不是接受模型任意提供的命令行字符串。
07

Runtime：子进程不是一句 spawn 就结束

核心文件：src/runtime/process.ts、src/tools/check.ts

Harness 需要把模型的工作变成真实工程行为：安装依赖、执行类型检查、运行测试。Runtime 负责处理进程生命周期和结果收集；工具层只决定允许运行哪一种检查。

输入控制

  • 显式 command、args、cwd。
  • timeoutMs 有效值检查。
  • maxOutputChars 有效值检查。
  • 命令参数与工作目录分离。

执行结果

  • exitCode 与 signal。
  • stdout / stderr。
  • timedOut。
  • stdoutTruncated / stderrTruncated。

超时与进程树终止

Runtime 默认超时为 120 秒，默认捕获输出上限为 10,000 字符。Windows 下用 taskkill.exe /PID … /T /F 尝试终止进程树；POSIX 下使用独立进程组，先 SIGTERM，再短暂等待后 SIGKILL。不同平台行为不同，因此有独立的 ProcessRuntime 测试。

固定检查工具的调用链

模型请求 run_check({ check: "test" })
          ↓
Policy：ask
          ↓
CLI 授权函数询问用户
          ↓
Registry 校验参数并执行 handler
          ↓
check.ts 校验 check ∈ {typecheck, test}
          ↓
Runtime.runProcess(...)
          ↓
收集退出码、stdout、stderr、超时和截断标记
          ↓
把真实检查结果作为 tool message 返回模型
非常重要的边界当前 Runtime 在宿主机上创建子进程。将 cwd 设置为沙箱路径只决定工作目录，并不自动限制该进程访问其他磁盘路径、网络或宿主机资源。真正的执行隔离仍需要 OS sandbox、容器或 VM 等机制。
08

Observability：让 Agent 的执行过程有证据

核心文件：src/observability/trace-writer.ts、trace-reader.ts、src/trace-cli.ts

每次 run 会产生结构化事件。Trace Writer 把每个事件写成单独一行 JSON（JSONL），包含 schemaVersion、记录时间和事件对象。Trace 文件放在原始项目的 .miniharness/traces/ 下，而不是复制到 Agent 工作区里。

当前事件类型

事件代表什么
run_started任务开始，记录 taskLength。
model_request第几步、消息数、可用工具数。
model_response是否有文本、模型请求了哪些工具。
model_error模型请求失败的原因；Writer 对常见 API Key / Bearer 模式做脱敏。
tool_started工具名称、调用 ID、step。
tool_finished成功与否、结果长度、执行时长。
run_finishedcompleted / max_steps / failed 与 step 数。

trace-cli.ts 可读取指定轨迹，或查找最近修改的 JSONL 文件并打印摘要。摘要包括记录数、状态、持续时间、模型请求/错误、工具调用/失败及每种工具的统计。

日志安全的边界当前 Writer 对 sk-... 与 Bearer token 这类常见模式做了脱敏，且新文件以受限权限创建；但这不等于对所有敏感信息做了完整数据防泄漏。不要把原始 prompt、私密文件内容或任意错误信息默认当成安全可公开日志。

Workspace：为什么先复制到临时目录？

核心文件：src/runtime/workspace.ts

最早的风险是：如果 Agent 的文件工具直接操作原始项目，模型一次错误的编辑就会污染真实工作区。当前设计先创建一个临时副本，文件工具绑定这个副本的根路径。原始项目与副本分离，修改先发生在副本中，再经 Diff 与审批决定是否回写。

创建工作区的具体步骤

  1. 通过 realpath 解析原始项目路径并确认它是目录。
  2. 在系统临时目录创建 miniharness-sandboxes。
  3. 使用 mkdtemp 创建唯一的 run-* 工作区。
  4. 递归复制项目，但排除指定目录和敏感配置；不复制符号链接。
  5. 遍历副本，为每个普通文件记录大小和 SHA-256。
  6. 把基线清单写到工作区旁边的 {workspaceRoot}.baseline.json。
  7. 返回 sourceRoot、workspaceRoot 和 cleanup 函数。

当前排除规则

类别当前排除项（示例）目的
版本 / 轨迹.git、.miniharness避免复制 Git 元数据和历史执行日志。
依赖 / 构建产物node_modules、dist、coverage、release、target、.turbo减少复制体积与无关差异。
敏感配置.env、.env.*、.npmrc、.pnpmfile.cjs避免把常见凭证、registry 配置与可执行 pnpm hook 带入副本。
文件类型符号链接与非普通文件避免把外部路径通过链接带入普通文件扫描。
当前生命周期上的一个细节工作区模块提供 cleanup()，但正常 Agent 任务结束后 CLI 会打印“Workspace retained for review”，把副本保留给用户审查。它不是自动清理的短生命周期容器；旧沙箱可能长期留在系统临时目录，后续可以增加显式清理命令与过期策略。

Diff 与 Baseline：变更检测和冲突检测不是同一件事

核心文件：diff.ts、diff-display.ts、workspace.ts、writeback-check.ts

Diff

“发生了什么变化？”

分别扫描 source 与 workspace，记录文件路径、大小、SHA-256。根据路径集合与 hash 判断新增、修改、删除。

Baseline

“源文件是否还是原来那一版？”

工作区创建时保存每个文件的初始 hash。准备写回时，将原始文件当前 hash 与基线比较，判断是否存在并发修改冲突。

三种文件变化

类型sourceworkspace含义
added不存在存在Agent 在副本中新建文件。
modified存在，hash 不同存在文件内容被修改。
deleted存在不存在Agent 在副本中删除文件。

为什么基线不能只记录时间戳？

文件修改时间可能受复制、同步、解压和工具行为影响；SHA-256 对内容做摘要，更适合检查内容是否变化。基线条目当前保存 size 与 sha256，其中冲突判断主要依赖 hash。

行级 Diff 如何生成？

diff-display.ts 先把 CRLF / CR 规范化为 LF，再按行切分，通过最长公共子序列（LCS）动态规划构建相似 unified diff 的行列表：空格前缀表示保留行，- 表示删除行，+ 表示新增行。

  • 文本文件最大读取大小：256 KiB。
  • LCS 动态规划最大单元格数：1,000,000。
  • 渲染行数上限：300 行。
  • 二进制文件或过大文件不会强行展示文本 Diff。
一次真实的调试教训Windows 路径使用反斜杠，但 Diff 记录统一用 /。最初路径校验把 src/demo.ts 转成了 src\demo.ts，导致嵌套文件被错误地标为 unsafe。修复方式是：内部相对路径统一用 /；真正访问文件时再用 path.join()。

Writeback：怎样把修改安全地交付回原项目？

核心文件：writeback-check.ts、writeback.ts、cli.ts

这是当前项目最有工程价值的一层。它解决的不只是“复制文件”，而是把模型在临时副本中的结果转换成一个经过检查、明确批准、可以验证的交付操作。

检查结果的三种状态

状态解释处理原则
ready当前文件状态与基线关系符合预期，且路径通过检查。可以进入人工审批，但不代表自动批准。
conflict源文件被用户改过、目标路径已存在或文件状态与预期不一致。阻止静默覆盖；需要重新审查。
unsafe路径非法、遇到符号链接、基线不合法或检查抛出安全异常。拒绝操作并检查原因。

当前写回引擎的具体行为

  • 要求调用方显式传入 approvedPaths；重复路径会被拒绝。
  • 批准路径必须仍是当前差异，并且预检查状态为 ready。
  • 新增文件使用 open(..., "wx")，避免直接覆盖已经存在的目标。
  • 修改文件先写同目录临时文件，再 rename 替换目标。
  • 删除前保存原始内容与权限位，以便失败时尝试恢复。
  • 记录已应用操作；后续出错时按反向顺序尽力回滚。
  • 写回结束后重新扫描差异，验证批准文件不再显示为差异。
TOCTOU：检查时与使用时之间的竞争窗口代码会在写回前、每个文件处理前重新检查，并对文件路径做 lstat 检查，但文件系统仍可能被外部进程并发修改。路径检查与后续写入不是一个原子操作，攻击者若能在两步之间替换路径或链接，仍可能制造竞态。
  • 多文件写回不是数据库事务；进程崩溃、磁盘错误或回滚自身失败时，可能留下部分结果。
  • 基线 JSON 是普通旁路文件，没有签名或可信存储保护；不能把它当作抵御恶意篡改的安全根。
  • 逐文件审批不是逐行审批；用户确认一个文件意味着批准该文件当前检测到的整体变更。
  • 临时文件替换、文件权限和 rename 的具体语义受操作系统影响，需要在目标平台做专门测试。

CLI 主流程：系统怎样被装配起来？

核心文件：src/cli.ts

cli.ts 是 Composition Root（装配根）：它读取配置，创建 Workspace，准备依赖，注册工具，创建 Provider 与 Agent，接上权限回调和 Trace Writer，最后运行任务。

CLI arguments
  ├─ --diff <workspace>  → 只看差异，不请求模型
  ├─ --apply <workspace> → 展示差异、逐文件审批、回写
  └─ <task text>
       ↓
     validate LLM_API_KEY / LLM_BASE_URL / LLM_MODEL
       ↓
     createSandboxWorkspace(process.cwd())
       ↓
     prepareSandboxDependencies(workspaceRoot)
       ↓
     register filesystem tools + run_check + echo
       ↓
     OpenAICompatibleProvider
       ↓
     Agent(maxSteps = 6, onEvent, authorizeTool)
       ↓
     agent.run(task)
       ↓
     print messages / status / retained workspace path

CLI 中最重要的职责

装配依赖

把 Provider、Registry、Tools、Agent、Trace Writer 和授权回调组合成可运行系统。Agent Core 本身不需要知道 CLI 的具体交互方式。

交互边界

解析 --diff 与 --apply，询问工具审批，打印执行轨迹与结果，并把临时工作区路径告诉用户。

依赖安装为什么单独处理？

当前 CLI 会在临时工作区中执行 pnpm install --frozen-lockfile --ignore-scripts，使用 120 秒超时和 8,000 字符输出上限。这样沙箱副本能有自己的依赖环境，而不依赖原始项目的 node_modules。聊天中曾遇到离线安装缺少 tarball 的错误：lockfile 已锁定版本，不代表本机 pnpm store 一定有所有包。当前源码不再把依赖安装固定为 offline 模式，但网络、镜像和依赖供应链仍是外部依赖。

命令入口

命令作用是否请求模型
pnpm dev -- "任务"创建工作区并执行 Agent 任务。是
pnpm dev -- --diff "工作区路径"扫描 source/workspace 并渲染 Diff。否
pnpm dev -- --apply "工作区路径"展示差异、预检查并询问每个 ready 文件是否批准。否
pnpm trace读取最近的轨迹并打印统计摘要。否
pnpm typecheck / pnpm test运行类型检查和单元测试。否
Windows 参数解析教训开发中出现过 pnpm dev -- "任务" 最终把 -- 一并传进程序参数的问题。当前 CLI 通过过滤 process.argv.slice(2) 中的独立 -- 来处理这个差异。这种小问题经常发生在 npm/pnpm script、shell 与 Node 参数边界上。

Agent Memory：当前有工作记忆，但没有完整长期记忆

这是用户最后明确提出的问题，也是后续理解 Harness 的关键分界。

当前消息历史放在哪里？

在 Agent.run(task) 方法内部，创建一个局部的 ChatMessage[] 数组。每次模型响应、工具调用和工具结果都会被追加到这份历史里。它是单次 run 的工作上下文，不是跨任务数据库。

Trace 为什么不是 Memory？

Trace Writer 会把生命周期事件写到磁盘；Trace Reader 能读取这些记录并统计模型请求、工具调用、失败与时长。但当前 Agent 在开始新任务时没有自动读取旧轨迹、提炼经验或检索相关事件，因此 Trace 只是持久化的可观测性数据。

如果以后要做长期记忆，最小设计应该是什么？

MemoryStore
  ├─ write(memoryItem)       # 保存经验
  ├─ search(query, scope)    # 检索相关记忆
  ├─ update(id, content)     # 修订 / 去重 / 过期
  └─ delete(id)              # 删除错误或过时记忆

任务启动：
  task + project context
       ↓
  MemoryRetriever.search(...)
       ↓
  relevance / trust / freshness filtering
       ↓
  注入有限的 memory context
       ↓
  Agent Loop

任务结束：
  trace + task outcome
       ↓
  candidate memory extraction
       ↓
  validation / user confirmation
       ↓
  MemoryStore.write(...)
不建议立刻加向量数据库先用 JSON/SQLite 实现明确的记忆结构、来源、创建时间、适用项目、可信度与过期策略，更容易验证价值。只有当检索规模、语义召回和跨任务经验确实需要时，再考虑 embedding 与向量索引。

工程问题复盘：那些报错为什么重要？

从开发聊天中抽取的关键问题，不是把错误当成挫折，而是理解系统边界。

USER · MODEL BOUNDARY

“为什么要安装真实模型的 SDK？我以为是给模型 API 和 Key，其他的自己写呀。”

ENGINEERING LESSON

SDK 只是调用外部模型的一种封装，不是 Agent Harness 的核心。项目用 ModelProvider 抽象接口，再以原生 HTTP Provider 实现 API 协议，从而把模型调用与 Agent Loop 解耦。

USER · FILE EDIT

“old text 也是模型返回吗？如果不是唯一匹配，当前代码是怎么做的？”

ENGINEERING LESSON

old_text 是模型在读过文件后构造的工具参数，但真正是否匹配由工具对磁盘上的实际内容进行验证。当前编辑工具要求精确、非重叠匹配次数恰好为 1；否则拒绝修改，不做猜测。

USER · TYPESCRIPT

“运算符 >= 不能应用于类型 number 和 {}。”

ENGINEERING LESSON

这类错误来自输入值类型未被充分收窄。文件搜索工具中的 max_results 需要通过明确的类型、整数和范围校验，不能让未经验证的未知值参与数值比较。

USER · WINDOWS PATH

“writeback-check 的嵌套文件测试被标记为 unsafe。”

ENGINEERING LESSON

Diff 记录统一使用 POSIX 风格的 /；若校验时把路径变成 Windows 的 \\，随后又按 / 拆分，就会把整个相对路径当成单一段。修复的关键是区分“规范化相对路径表示”与“本地文件系统访问路径”。

USER · STRICT TYPES

“exactOptionalPropertyTypes 报错，number | undefined 不能赋给 number。”

ENGINEERING LESSON

在开启 exactOptionalPropertyTypes 后，originalMode?: number 表示可以不提供属性，但提供时值必须是 number。若代码显式传入 undefined，类型需要明确允许它，或使用条件展开只在有值时提供属性。

USER · DIFF TEST

“相同文本和 Windows/Unix 换行符的测试返回了未修改的行，而不是空数组。”

ENGINEERING LESSON

Diff 的职责是显示变化，不是把全部上下文都当成变化。先规范化 CRLF / CR，再判断两组行完全一致；一致时直接返回空数组，避免进入 LCS 回溯逻辑。

USER · DEPENDENCY INSTALL

“Sandbox dependency preparation failed：offline tarball 缺失。”

ENGINEERING LESSON

lockfile 固定了依赖版本和解析结果，但离线安装还要求本地 store 中存在所需 tarball。离线可复现性需要提前缓存依赖或准备镜像；当前 CLI 的依赖准备使用 frozen lockfile 与 ignore-scripts，但仍依赖包管理器和网络环境。

USER · GIT

“gitignore 有 node_modules，但是大量文件仍被 Git 追踪。”

ENGINEERING LESSON

.gitignore 只阻止尚未跟踪的文件被默认加入；已经被 Git 索引跟踪的文件仍会继续显示修改。要停止追踪，需要有意识地从索引移除（例如 git rm --cached）并提交变更，而不是只增加 ignore 规则。

USER · PROCESS / CWD

“const workspaceRoot = process.cwd() 是调用终端开进程吗？switch 是做什么？”

ENGINEERING LESSON

process.cwd() 返回当前 Node 进程的工作目录，不会自己启动终端或新进程。switch 是按消息 role 等离散值选择不同处理分支的控制语句；在 Provider 中用于把 system/user/assistant/tool 消息转换为不同的 wire format。

这些问题分别锻炼了什么能力？

问题类型底层工程能力
Provider / API 协议接口抽象、协议适配、外部依赖隔离。
TypeScript 类型错误输入边界、运行时校验与静态类型的一致性。
Windows 路径与进程跨平台抽象、路径规范化、进程生命周期。
Diff 与基线冲突内容寻址、并发状态检测、交付一致性。
Git ignore 与缓存版本控制索引、可复现构建、仓库卫生。
端到端验证从局部函数正确性走向系统行为验证。

安全边界：当前做了什么，不能宣称什么？

这是理解 Harness 工程成熟度时最需要保持准确的部分。

维度当前措施剩余风险 / 缺口
文件访问限制 workspace root、realpath 检查、阻止常见敏感路径、限制文件大小、拒绝符号链接访问。文件系统并发竞态仍可能发生；应用层路径检查不等于基于文件描述符的强隔离。
工具执行Registry 只执行已注册 handler；Policy 未知工具默认 deny；edit_file 与 run_check 需要 ask。工具本身仍需逐个审计；授权策略不是 OS 权限边界。
命令执行当前 Agent 暴露的是固定检查命令；Runtime 有超时、输出上限、进程树终止。进程在宿主机运行；工作目录不是文件访问限制；依赖安装也会访问网络与包源。
日志JSONL 结构化记录，常见 API Key / Bearer 模式脱敏，限制输出与文件权限。脱敏模式不覆盖所有秘密；日志可能含任务元数据和错误信息。
工作区副本与源项目分开，排除敏感文件和符号链接，基线 hash 检查。不是容器；进程仍拥有宿主机用户的权限；基线 JSON 未签名。
回写显式批准、预检查、逐文件重查、独占创建、临时替换、尽力回滚、后置验证。不是多文件原子事务；TOCTOU 与崩溃场景未被彻底消除。
远程 / 容器尚无 Docker / VM / Remote Workspace Driver。不适合直接作为不可信代码的强隔离执行环境。

用一句话描述当前安全等级

准确说法MiniHarness 具备基础的工具治理、本地副本工作区、变更审查与受控回写机制，能降低误改和意外覆盖风险；但目前没有实现完整的操作系统级执行隔离，不能把它称为生产级安全沙箱。

为什么 Docker 可以先放一放？

因为学习目标是理解 Harness 的控制面与执行面。当前先把 Agent Loop、Tool Registry、Policy、Runtime、Trace、Workspace、Diff 与 Writeback 串起来，已经形成了一个有价值的 MVP。Docker 是下一层执行环境后端，而不是理解 Agent Loop 的前置条件。

未来要接 Docker，合理做法是抽象 Environment / Workspace 接口，让本地执行与容器执行共享上层 Agent Core；而不是把 Docker 调用直接散落进每个工具 handler。

术语表：把项目语言统一起来

以后读 OpenCode 或其他 Harness 时，可以沿用这套概念对照。

术语在本项目里的含义
Agent Harness围绕模型建立的运行框架：上下文管理、工具执行、策略、状态、可观测性与结果交付。
Agent Loop模型请求、工具调用、工具结果回填、下一轮决策，直到结束条件触发的控制循环。
Provider模型服务适配层，把内部消息与外部 API 协议连接起来。
Tool Call模型提出的结构化工具调用请求；不是工具已成功执行的证明。
Registry工具定义与执行 handler 的注册表，按名称查找并分发。
Policy决定工具调用是允许、需审批还是拒绝的规则。
Runtime管理进程、超时、输出和执行结果的底层机制。
Workspace / Sandbox当前任务操作的工作区副本；本项目是本地临时目录，不是 OS 级沙箱。
Baseline工作区创建时记录的文件清单和 hash，用于检查源文件是否发生外部变化。
Diff比较源目录与工作区，识别新增、修改、删除文件，并渲染行级变化。
Writeback把经过审批的工作区文件变更应用回原项目。
TOCTOUTime-of-check to time-of-use：检查状态与实际使用之间发生变化导致的竞态。
Trace描述执行过程的持久化事件记录，供复盘和统计。
Working Memory当前 run 的消息历史，保存在内存并用于后续模型请求。
Long-term Memory跨任务保存、检索、更新并重新注入模型上下文的经验系统；当前尚未实现。
Docker Driver未来可能新增的容器执行后端；当前代码中不存在。

最后总结：你实际搭建出来的是什么？

一份可继续演化的工程原型，而不是一个黑盒脚手架。

你搭建的不只是“能调用 DeepSeek 的脚本”，而是一个具备清晰边界的本地 Agent Harness 原型：模型负责提出下一步，Agent Loop 管理决策循环，Registry 与 Policy 控制工具执行，Runtime 管理进程，Trace 保存运行证据，Workspace 把编辑与原项目分离，Diff 与 Baseline 识别变更和冲突，Writeback 把经过批准的修改交付回原项目。

这段开发最值得保留的经验，不是某一段 TypeScript 代码，而是工程问题的分层方法：当系统出错时，先用真实输出定位原因；把外部协议、执行机制、权限决策和状态管理分开；为关键不变量写测试；最后用端到端流程证明各模块能够共同工作。

当前结论本地 Agent Harness MVP 的主要闭环已经建立。Docker 可以暂缓；长期 Memory 尚未实现；生产级安全隔离、崩溃恢复和完整的系统级评测仍是后续工作。下一步最合理的动作是冻结版本、整理 Git 与 README，再按真实需求决定是否扩展。
